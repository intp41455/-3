# 03 · 数据层与问卷规范

`src/data/` 是内容的单一真源。本文说明字段语义与**扩写规范**——即「新增一页幻灯片 / 新增一个问题时该怎么写」。

| 文件 | 导出 | 规模 | 消费方 |

## 一、`slidesData.ts`

### 完整字段

```ts
interface SlideData {
  id: number;              // 内部 ID（与 slideNumber 一致）
  slideNumber: number;     // 页序，用于标题前缀「P{n}」
  category: string;        // 分类，用于标题前缀与导航
  badge: string;           // 右上角英文徽标，如 'Cover Slide' / 'Agenda'
  actionTitle: string;     // ★ 主标题——"动作导向"写法，见下
  subTitle?: string;
  objective: string;       // 本页要达成的目标（给演讲者看，不出现在正文）
  layout: SlideLayout;     // 10 种页型之一
  cards?: SlideContentCard[];
  table?: SlideTable;
  flowSteps?: { step: string; label: string; desc: string; role: string; highlight?: boolean }[];
  pyramidLevels?: { level: string; title: string; desc: string; target: string }[];
  timeline?: { day: string; phase: string; tasks: string[]; owner: string }[];
  highlightBanner?: string;
  speakerNotes: string;    // ★ 逐字稿（必填）
}

interface SlideContentCard {
  title: string;
  badge?: string;
  items: string[];
  type?: 'primary' | 'secondary' | 'accent' | 'warning' | 'success';
}

interface SlideTable {
  headers: string[];
  rows: string[][];
}
```

### 写作规范：`actionTitle` 是动作，不是名词

观察现有 15 页的标题写法：

| 页 | 标题 | 特征 |
|---|---|---|
| 3 | 从「对话玩具」到「数字员工」：信息完备度决定智能体上限 | 有转折 + 有结论 |
| 7 | 穿透业务肌理：找准数据堵点就是找准 AI 落地价值点 | 「A 就是 B」的判断句 |
| 10 | 筑牢安全堤坝，打通外部视野：稳健与敏锐兼备 | 对偶 + 价值主张 |

**共同点**：标题本身就在讲结论。对比反面写法——「模块 3 深度解析」「数据治理说明」——后者只是目录标签，听众无法从标题获得任何信息。

### 写作规范：`objective` 是给演讲者的自我提醒

```ts
objective: '清晰呈现宣贯脉络与协同路径，确保各团队统一节奏'
```

这个字段不渲染到页面上，它的作用是：**半年后你自己翻回来看，能立刻想起这一页当时是为了解决什么沟通问题**。

### 写作规范：`speakerNotes` 要能直接念

写「口语陈述」，不写「要点复述」。第 1 页示例：

> 各位领导、各位同事，今天我们正式启动多智能体系统部署的前置调研工作。大模型落地的核心不是简单接入一个对话框，而是让 AI 智能体像数字员工一样融入我们的业务流程。在动工之前，我们需要一张详尽的「数字地形图」，这就是我们今天启动《信息采集标准问卷》的目的。

三句话完成三件事：**开场定位 → 纠正认知偏差 → 给出本次会议的行动理由**。

### 新增一页的流程

1. 在 `SLIDES_DATA` 末尾追加一个对象（`slideNumber` 递增）
2. 选一个已有的 `layout`，按该页型的字段要求填内容
3. `speakerNotes` 必填
4. **检查 `slidesExport.ts`**：如果新页用了某个可选字段，确认导出器的灌入分支覆盖了它（当前覆盖 `cards` / `flowSteps` / `pyramidLevels` / `table` / `timeline`）
5. 数字变了同步改——第 2 页 `cards` 里写了「10 维矩阵」，第 14 页甘特写了「10 个工作日」

> 页数从 15 变成其他数字时，注意 `slidesExport.ts` 里的进度文案写死了「15 页」：
> `step: '演示文稿创建成功，正在批量构建 15 页幻灯片内容...'`

### 新增一种页型（`layout`）

1. `src/types.ts` 的 `layout` 联合类型加成员
2. `PresentationViewer.tsx` 加渲染分支
3. `slidesExport.ts` 加对应的内容灌入逻辑
4. 否则 Slides 导出会生成一个只有标题栏的空白页

## 二、`questionnaireData.ts`

### `QUESTIONNAIRE_METADATA`

```ts
{
  title: '企业多智能体系统部署 · 信息采集标准问卷',
  version: 'V1.0',
  stage: '方案策划启动前 1-2 周',
  period: '建议 7-10 个工作日',
  confidentialStatement: string,   // 保密声明
  instructions: { item: string; desc: string }[]   // 填写须知（5 条）
}
```

`instructions` 的 5 条：

| item | desc |
|---|---|
| 发放时机 | 方案策划启动前 1-2 周，预留客户准备数据的时间 |
| 填写方式 | 由企业项目对接人牵头，协调各业务部门配合填写 |
| 填写周期 | 建议 7-10 个工作日 |
| 填写原则 | ① 能提供数据/文档的直接附上；② 暂无精确数据的提供估算；③ 确实无法回答的标注「待调研」 |
| 提交格式 | 建议提交本问卷的 Markdown 或 Word 版本，并将相关数据附件打包一并提交 |

> 「填写原则」这三档（直接给 / 给估算 / 标待调研）是关键设计——它把「答不上来」变成了一个**被允许且有标准写法的选项**，避免填报人因为某一题答不上来就整份拖着不交。

### `QUESTIONNAIRE_SECTIONS`

```ts
interface QuestionnaireSection {
  id: string;             // 'sec1' ~ 'sec10'
  number: string;         // '第一部分'
  title: string;
  description: string;    // 本维度在问什么、为什么问
  subsections: {
    title: string;                                    // '1.1 企业概况'
    questions: QuestionnaireQuestion[];
    exampleData?: ExampleTableData;                   // 示例表格
  }[];
}

interface QuestionnaireQuestion {
  question: string;
  explanation: string;    // ★ 必填
  example?: string;       // 21 个问题带范例
}

interface ExampleTableData {
  headers: string[];
  rows: string[][];
}
```

### 写作规范：`explanation` 是必填的核心字段

**这是本问卷与「随便列几个问题」的分界线。** 每一问都要交代口径，而不是只丢一个标题。

| 问题 | ❌ 只有标题 | ✅ 带 explanation |
|---|---|---|
| 分支机构数量 | 分支机构数量？ | 含子公司、分公司、直营机构等 |
| 年营收规模 | 年营收？ | 尽可能提供近一年数据或区间 |
| 数据标准化程度 | 数据标准化程度？ | 各系统间数据格式是否统一？是否存在「数据孤岛」？ |
| 现有 IT 系统清单及供应商 | 有哪些系统？ | 列出核心系统（ERP/OA/CRM/HIS 等）及供应商 |

### 写作规范：`example` 要给真实颗粒度

范例的作用不是「示范格式」，而是**告诉填报人写到什么详细程度算合格**：

```ts
{
  question: '分支机构数量',
  explanation: '含子公司、分公司、直营机构等',
  example: '7 家机构（西安 4 家、成都 2 家、云南曲靖 1 家）+ 30 余个日间照料中心'
}
```

一个合格的范例必须包含**可验证的细节**（地域分布、数量级）。若是「约若干家」这样的范例，等于没写。

### 写作规范：`exampleData` 用于表格类问题

当某一小节需要填的是**结构化表格**时，用 `exampleData` 直接给一张填好的示例表——比文字描述有效得多。

### 新增一个小节的检查清单

1. `id` 唯一（`secN` 规则）
2. `number` / `title` / `description` 齐全，`description` 要说清「为什么问这个」
3. 每个 `question` 必带 `explanation`
4. 关键问题尽量带 `example`（用真实数字，不用占位符）
5. 问题总数变化时同步检查 README 与文档里的「78 问」是否需更新
6. 涉及真实企业信息的示例，评估是否需要脱敏

## 三、`MermaidWorkflow.tsx` 的双数据源（已知不一致）

`RAW_MERMAID`（流程图）与 `STEPS`（9 张卡片）是**两份独立数据**，改动需手工同步。

当前可以观察到的不一致：`RAW_MERMAID` 共 **10 个节点**（A–J，其中 `G` 是菱形判定节点 `G{指标与接口是否完备？}`），而 `STEPS` 是 **9 条**（`id` 依次为 `A B C D E F H I J`，**跳过判定节点 G**）。

| 数据 | 内容 |
|---|---|
| `RAW_MERMAID` | A → B → C → D → E → F → **G{判定}** → H → I → J，其中 `G -->\|否\| D` 形成回退分支 |
| `STEPS` | STEP 01~09，`id` 对应 A/B/C/D/E/F/H/I/J 九个**执行**节点 |

两者靠 `id` 字段做隐式对应，**没有任何代码校验这个对应关系**——改坏了对不上不会有任何报错，只是卡片与图不一致。

**建议的收敛方向**：从 `STEPS` 生成 Mermaid 源码（把连边关系也放进 `StepNode`），或反过来从 Mermaid 解析出步骤列表。当前实现下，任何流程变更都必须**同时改两处并且人工核对节点对应关系**。

## 四、通用维护约定

| 约定 | 说明 |
|---|---|
| **数字只出现一次** | 页数、问题数、维度数、工作日数在多个文件里重复出现。改动后全局搜索确认 |
| **中文文案不要用直角引号转义** | 数据里用的是中文引号「」，与代码引号不冲突，可放心写在单引号字符串里 |
| **含英文缩写的字段保持大小写** | `API` / `IT` / `SOP` / `ROI` / `KPI` 统一大写，便于全文检索命中 |
| **`badge` 字段是英文** | `'Cover Slide'` / `'Agenda'` / `'Workflow'` 等，用于视觉分区，与中文标题并存 |
